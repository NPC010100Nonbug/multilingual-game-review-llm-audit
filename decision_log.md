# Decision Log

| Date | Decision | Rationale |
|---|---|---|
| 2026-07-28 | Binary main label (unfair = 1/0), with an `uncertain` flag as a separate field | With ~25-33 reviews per language, a 3-class scheme spreads counts too thin for stable agreement statistics; uncertainty is still captured in its own field |
| 2026-07-28 | Raw review texts are kept out of the public repo (`data/raw/` and `data/processed/` are gitignored); only labels, review_ids and a small demo sample are published | Re-publication rights for Steam reviews are unconfirmed and full texts could expose user information; reproducibility does not require the data itself, since anyone can rebuild the corpus with the collection scripts and review_ids |
| 2026-08-04 | Pivot from an API-only measurement *audit* to a *training* project: fine-tune a multilingual model, not just prompt an LLM | Build hands-on annotation + fine-tuning experience (the two skills Yifan wants to develop); the lab follow-up deadline is relaxed, so depth beats speed. The original application described "API only, no training" — if this repo is ever sent to the lab, the README must state the training design accurately |
| 2026-08-04 | Human labels become a **gold test set** (~100+/language, hand-labeled, blind, per frozen codebook); a larger **LLM weak-labeled set** (thousands/language) becomes the **training set** | A solo beginner cannot hand-label training-scale data; using LLM labels as training signal is standard **weak supervision / distillation**. The human gold set stays the only trusted evaluation ("exam"), never used for training |
| 2026-08-04 | Add a **cross-lingual transfer** evaluation (train on one language, test on the others) and a three-way comparison (fine-tuned model vs LLM zero-shot vs human gold) | This is the measurement question MilaNLP/AISS care about, and it turns the project from a single-number audit into a real research contribution |
| 2026-08-04 | Training runs on the local ASUS laptop (RTX 4060, 8GB, CUDA); collection/annotation/analysis stay on the Mac; Git is the sync bridge between the two machines | Fine-tuning XLM-RoBERTa-base fits in 8GB; no cloud GPU (Colab) needed. Model `large` or very large data remain a fallback for Colab |
| 2026-08-04 | For appid 730 (Counter-Strike), keep only reviews with `timestamp_created >= 1695772800` (2023-09-27, the CS2 launch) | appid 730 also carries the pre-2023 CS:GO era, which is effectively a different game; date-filtering keeps the "CS2" construct consistent. Battlefield 2042 (1517290) needs no such filter |
| 2026-08-04 | Japanese is the binding language (~14k combined raw reviews); English/Chinese will be down-sampled toward the Japanese count | Keeps the three languages comparable so cross-lingual differences aren't confounded by sample-size imbalance |
| 2026-08-05 | Collect with `purchase_type=all`, not the API default `steam` | A probe (`00_probe_counts.py`) held everything constant and varied only this flag: CS2 Japanese went 6,767 → 11,259, matching the store page's 11,262. The default silently drops key-activated / free-acquired reviews; the effect is largest on free/competitive titles (CS2 zh 3.47x) and negligible on paid single-player ones (Elden Ring ja 1.07x). `all` recovers the full public pool, which matters most for the Japanese bottleneck |
| 2026-08-05 | Add **Elden Ring** (appid 1245620) as a third, different-genre control game | Breaks the shooter genre-monoculture of CS2 + BF2042; supplies hard negatives (praise, and "hard ≠ unfair" cases) so the model learns the *perceived-unfairness* construct rather than "shooter complaint = unfair". Japanese pool under `all` = 5,940, well above the ≥1,000 bar |
| 2026-08-05 | Japanese pool under `purchase_type=all` ≈ 20.4k across the three games (CS2 11,259 + BF2042 3,160 + Elden Ring 5,940), superseding the earlier ~14k estimate | More Japanese headroom than expected. Caveat: CS2's 11,259 still includes pre-2023 CS:GO reviews and will shrink after the date filter (≥ 2023-09-27); the true usable Japanese count is only known after pagination. EN/ZH are still down-sampled toward the post-filter Japanese count |
| 2026-08-05 | CS2 has only **1,943** Japanese reviews from the CS2 era (≥ 2023-09-27); the other ~9,300 of its 11,259 JA reviews are CS:GO-era and are correctly excluded by the date filter | Verified empirically: paginating CS2/ja reached exactly the launch-date floor (oldest kept review = 2023-09-27), so 1,943 is the true usable count, not a pagination artifact. This validates the date-filter decision. Combined usable Japanese ≈ 1,943 (CS2) + 3,000 (BF2042) + 3,000 (Elden Ring) ≈ 7.9k, still well above the ≥3,000/language need |
| 2026-08-05 | **Deep-collection experiment settles the API ceiling: Steam's `recent`+cursor feed is capped far below `total_reviews`, so full back-collection to 2023 is impossible for dense cells.** `01b_deep_collect.py` (resumable, purchase_type=all) paged every EN/ZH cell to `reached_end` (an empty page = the true bottom of the served feed). Hard proof: CS2 Chinese has **1,404,644** total reviews but the feed gave out at **42,797 (~3%)** at 2026-03-05; CS2 English gave out at 118,372 at 2026-02-13. BF2042 English is the only cell that reached game launch (133,203, back to 2021-11-19). | Turns the earlier "residual limitation" from a guess into a measurement. **Consequence for alignment:** compare cross-lingually inside each game's **common window** = the latest of the three languages' oldest dates — bound by **Chinese** in all three: CS2 ≈ 2026-03→now (~5 mo), BF2042 ≈ 2023-11→now (~2.7 yr), Elden ≈ 2025-05→now (~15 mo). Two constraints coexist: Chinese binds the window's *reach* (left edge), Japanese still binds sample *size* within it (sparse). Down-sample EN/ZH by month to the JA count inside the window; document the depth ceiling in the README |
| 2026-08-05 | **Temporal-window confound identified and (partly) addressed.** With `filter=recent` + a fixed per-language target, a fixed count covers very different time spans per language (CS2/en 3,000 ≈ 2 days vs CS2/ja ≈ 2 years). Fix: collect each game's Japanese in full to define its time floor, then collect EN/ZH back to that floor (early-stop once older; safety cap 15k) so the raw pools share a window; later down-sample by month (stratified) toward the JA count | Cross-lingual differences must not be confounded with time. Chosen over "document only" and over "restrict all to a short common window" (which would starve Japanese). **Residual limitation:** Steam's API is newest-first with no date-range query, so the densest cell (CS2/en) still cannot reach the JA 2023 floor within the cap (~10-day window); this is documented in the README limitations, not hidden |
